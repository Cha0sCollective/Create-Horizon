# Contraptions 005 — stationary bearing capture decision

Status: **proposal only**, 6 November 2026. No world capture, bearing content, renderer, host change or schema change is implemented by this packet. The owner must approve this exact capture scope before implementation. Its first gate is a PASS for the Contraptions-004 foundation's actual saved-owner, independent-peer VIEW and normal cold-reopen packet on frozen root 007 `f732bd481cfc3d9c4720bc51e4a31e7385e18020`. The earlier 005 run with no peer receipt remains HOLD and cannot satisfy that gate.

## Reuse and the actual gap

The live port already has the read-only `contraption_preflight::plan_scene`, the portable `Assembly::capture` and `Assembly::landing` planners, and the private version-1 entity `AssemblyRecord`/`AssemblyView` codecs and carrier guards. `Assembly::capture` discovers and snapshots; it never removes a block. The owner foundation presently scans a synthetic display and queues a saved VIEW on tracking; it does not create a carrier or advance custody. The [current upstream main](https://github.com/Delete228/create-horizon/tree/dd0f3141a33851ac20fa98b807a6532471dba727) has no `mixins/create/engine/src/core/contraption/assembly.rs`; the separately staged [contraption core](https://github.com/Delete228/create-horizon/tree/affd76f1301b61b264c08072f9a7aa8d3be0343c) remains the source of this copied planner. Its [stage document](https://github.com/Delete228/create-horizon/blob/affd76f1301b61b264c08072f9a7aa8d3be0343c/docs/contraptions.md) also leaves native custody, writes and rendering to the adapter. This packet requests no upstream edit.

The private active content has no `create:mechanical_bearing` block definition, block entity, item/model or connection. Thus the existing preflight's actual-controller check is closed in a normal world. That is the first mod-content gap. Register only an upward bearing for the disposable pilot, with placement and a real block entity; leave powered rotation, generalized kinetic binding and other facings to a later decision. A fixture-gated one-shot capture/release request may drive this **stationary custody test**; it must be clearly labeled diagnostic, not playable bearing behavior. The portable `Bearing::tick` cannot start assembly at zero theoretical RPM, so silently treating this pilot as a normal zero-speed bearing would be false (`core/contraption/bearing.rs:70-103`).

The host already exposes loaded guarded state reads (`native_world_read.rs:121-139`), exact state lookup (`horizon-world/src/registry.rs:161-171`), one-state `native_set_block` (`game/native_hooks.rs:8349-8381`), loaded-chunk `native_summon` (`game/native_entities.rs:141-183`), UUID-backed entity attachments (`game/mod_api_host.rs:97-133`), and world atlas quads (`game/native_world_draw.rs:125-164`). No missing public API is demonstrated for this two-cell pilot. `native_set_block` takes a `BlockStateId`, not an arbitrary `BlockState`, and a failed or no-change result is not a write receipt. Before any removal, resolve exact `minecraft:air`, slime, and oak-log states through `BlockRegistry::id` and verify their round trips. If any state or the new controller is absent from the **actual built registry/palette**, stop; do not replace properties with a default or add a generic palette path. This is a runtime gate, not a claim from source inventory.

## Exact fixture and ownership

Use one disposable loaded Overworld chunk, with an upward `create:mechanical_bearing` and its block entity at `[8,63,8]`, front `minecraft:slime_block` at `[8,64,8]`, and one bonded `minecraft:oak_log[axis=z]` at `[8,64,9]`. The two cells, bearing, carrier, inspected neighboring cells and restore destinations stay in that chunk. No third attached block, block entity in a captured cell, glue, chassis, item, fluid, actor, passenger or body may be admitted. Source and restore positions are identical; angle stays exactly zero. The log keeps axis `z`. This tests transfer of custody out of the world and back **without** a rotating landing, swept motion or contact claim. The same preflight must reject an unloaded or out-of-chunk neighbor, foreign state, extra adhesion, invalid controller, unknown state or existing owner claim before a write.

Create one persistent `minecraft:block_display` carrier at `[8.5,64.0,8.5]`, with no drawable `block_state`, the existing private owner marker, an explicit unique carrier UUID and an independent `AssemblyId`. Use the approved version-1 `Holder::Entity` RECORD and derived VIEW on that same carrier; no controller-owned copy of the snapshots. The controller may retain only an advisory assembly link. Prove that a summon with explicit UUID and typed attachments yields a live decodable owner, the expected UUID and a guarded carrier **before** touching either source. If provisioning fails or leaves a marked but malformed carrier, stop and diagnose while the two world blocks remain; do not bypass the guard or capture with an unowned record. The runtime numeric entity ID is never a saved identity.

## Proposed single-chunk custody sequence

1. On an authoritative request, read the exact two source states and all relevant loaded neighbors with the guarded read API. Run the existing portable preflight at zero degrees. Reject a competing/duplicate owner or reserved cell and verify the two source states, bearing identity, carrier chunk, exact state IDs and empty or own restore targets. This is planning only.
2. Provision and read back the carrier's `Preparing` RECORD and matching VIEW with `source_removed=false`, `target_placed=false` and explicit last observed identities. Only that verified owner may authorize source removal. Recheck each source immediately before a checked `native_set_block(..., air, 3)`; read back air and update that cell's verified progress before starting the next removal. A no-change return is interpreted against the readback and recorded identity, never as automatic success.
3. Once both exact source cells are verified air, set `Captured` in RECORD and derive/queue its VIEW. Hold angle zero and leave the bearing/controller in place. There is no motion tick, world proxy, physical contact, or actor/inventory update in this pilot. Reject any attempt to add cargo or move the carrier; the existing five guard surfaces still apply.
4. On an explicit fixture release, controller removal request, or normal reconciliation after reopen, recheck both target/source positions and nearby authoritative bodies. Mark `RestorePending`; place each original state only into verified air with checked single-state writes and readbacks. If a write fails, a third-party state/body occupies a target, or a controller disappears, retain the carrier and record for retry. Never overwrite a foreign block or discard the remaining snapshot. When both cells are exactly present once, mark `Settled`, verify the record, then permit carrier removal. A second capture request must refuse while any prior owner is live or corrupt.

The `Preparing` record is an in-memory owner before the first deletion; these are several world/attachment writes, not a multi-block transaction or a forced durable checkpoint. On a partial capture, compare each recorded progress bit with the actual world state before deciding whether to continue removal or restore. If a saved identity and world state disagree, stop with custody retained for inspection. Normal same-chunk unload and cold reopen must rebuild the loaded owner scan and reconcile from the saved entity and block chunk. Abrupt power loss or independently torn entity/chunk saves are outside this ordinary-restart claim. The owner is removed only after exact restoration readback, including when the controller was replaced.

## Client and save boundary

The RECORD stays unsynced; VIEW is the only client projection. On `Captured` or `RestorePending`, use the existing tracking-start VIEW resync and a checked VIEW update for the phase change. Draw the two state-only cubes from VIEW via `native_world_submit`/`native_world_quad`, with the exact slime and oak-log side/end sprites, depth and orientation checked in integrated and independent dedicated-peer images. The air display itself draws no cargo. At zero angle the view is stationary; client rendering is never a world block or custody authority. A client may use its loaded block copy to avoid drawing a cell still present in the world during a partial `Preparing`/restore pass; it must not infer server progress from that copy. Missing atlas sprites or an undecodable/mismatched VIEW are a visual HOLD, not permission to remove the owner.

Require a normal saved `Captured` reopen with both source cells air, one retained carrier UUID/RECORD, exact VIEW delivered to a fresh real peer, then safe restore to the original two positions. Also require a partial-removal failure, a blocked release and retry, controller replacement, duplicate/corrupt-owner refusal, carrier `/kill`/native-remove and `/tp`/native-move refusal, and no third-party cell overwrite. Verify source and final cell queries, entity NBT, actual peer frames and normal process exits. Run only under Operations' single build/game lease, with a new disposable world and frozen source/binaries; preserve failed receipts. No acceptance of moving bearing, quarter-turn log rotation, swept collision, vanilla collision, Java parity, train/storage cargo or crash atomicity follows from this test.

## Decision

**Request owner approval for this finite diagnostic capture pilot only after Contraptions-004 runtime PASS.** It adds one private bearing controller/content entry, one fixture-gated stationary capture/release path and two-cell VIEW drawing using the existing version-1 entity owner. It does not authorize a production capture implementation yet. If owner approval is given, require fresh source review and exact root-granted build/runtime gates; if the foundation, inline owner provisioning, registry state resolution, explicit deletion/relocation guards or save/peer proof fails, stop at that evidence and return a smaller gap finding rather than expanding the host or owner schema. Powered rotation, a normal activation path and broader structure capture need a separate packet.
