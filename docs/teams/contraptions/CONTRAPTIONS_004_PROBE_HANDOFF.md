## Exact gate and hooks

Set `CREATE_HORIZON_OWNER_PROBE=1` separately on the dedicated server child and real Horizon peer child. The server process must have a current-directory basename `contraptions-004-probe-server`, and its loaded world-root basename must be `contraptions-004-probe-world`. The peer process must have a current-directory basename `contraptions-004-probe-client` and be in `minecraft:overworld`. Every other environment value or profile is inert. The server hook is the existing `level_tick_post`; the peer hook is the existing `frame`, after normal packet processing. Both use Create's existing game-log sink for a new `Create owner probe:` JSON line and emit once per child process only after the exact fixture is recognized.

The server requires a `minecraft:block_display` at `[8.5,64.0,8.5]`, UUID `[5,6,7,8]`, exact private marker, a decodable canonical record with independent assembly ID `[1,2,3,4]`, the two specified inert state-only cells, `Preparing`, zero pose and no removed/placed cells or removal request. The ordinary loaded-owner scan must return this one active ID without refusal. Only then does the probe call `native_move_entity` once toward `[9.5,64.0,8.5]` and `native_remove_entity` once. It logs scan vectors, both return values, retained presence and actual position. A correct guard run reports `discovered=true`, both returns `false`, retained `true`, and unchanged position. If the scan refuses the fixture, the one-shot line reports `discovered=false` and skips both API calls.

The peer identifies the server's spawn UUID from its received entity ID, requires a tracked display and the exact view payload, decodes `VIEW` from its actual received attachment map, and logs the two visual cells and whether canonical `RECORD` was erroneously present. A correct peer line reports `canonical_record_present=false`. This is packet receipt, not a renderer or gameplay view.
